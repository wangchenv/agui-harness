# UI / UX 设计契约

这是草案：按真实任务和现有品牌补全，不用通用后台模板代替设计。

## 角色与主任务
分别写用户和运营人员的目标、使用频率、信息密度、最重要的判断和主操作。给出任务成功、误操作和审核耗时基线。

## 信息架构与关键屏幕
每个屏幕指定主任务、主操作、关键证据、次要动作、助手所在位置，以及返回普通操作流程的方式。先定义任务路径，再选聊天框/卡片/表格/表单/时间线；不把所有流程塞进对话气泡。

## 视觉方向
复用已有design system；没有时定义字体、层级、颜色角色、空间节奏、边框/阴影和动效。注明品牌偏好、密度选择与原因；tokens.json是实现来源，不允许随处硬编码。

## 组件与状态
component-inventory.json记录组件、状态、动作、键盘/名称/focus，以及桌面/平板/移动组织方式。补齐loading、empty、error、partial、validated、submitting、committed、unknown、stale等适用状态；不靠颜色单独传递含义。

## 关键交互
写出用户如何检查事实、审查差异、批准或拒绝、撤销可逆操作、知道执行结果、断流恢复、处理未知结果。主操作只有在可信状态成立时可用。

## 可访问性与响应式
校验文本对比度、真实DOM焦点顺序、语义名称、键盘完成主任务、焦点可见/恢复、读屏状态提示、缩放重排和reduced motion。检查器仅验证声明颜色对，不等于WCAG合规。

## 原型与视觉验收
prototype路径指向可运行原型或实现；记录至少桌面/平板/移动视口、真实截图、发现问题与修复。视觉review检查层级/排版/遮挡/溢出/状态明确；没有实际打开不能写“已视觉验收”。

## 证据与未验证项
把自动tokens检查、真实浏览器UI测试、截图视觉review、真实人员任务效率分开。原型通过不能替代后端或模型验证；缺少测试环境时明确缺口。
