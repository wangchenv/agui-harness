# 评测：用真实任务和业务状态证明有效

本文件面向 coding agent 的验证工作；控制编号 H01–H12 与构建规范一致。
交付的不只是分数，还包括可复跑用例、业务 oracle、失败轨迹和上线判定。
故障注入按 [failure-matrix.md](failure-matrix.md)执行；运行时约束见 [runtime.md](../../agui-build/references/runtime.md)。

## 1. 先写任务定义与人工基线〔H11〕

从实际使用者选取一个完整任务单元，例如“调整指定排班并通知受影响人员”。
明确入口状态、完成标准、允许范围、不可触碰资源、授权来源和最晚完成时间。
任务成功必须可从业务记录判断，不能定义成“回答看起来正确”或“工具被调用了”。
测量现有人工流程：主动操作分钟、端到端历时、操作次数、复核时间、错误/返工率。
同样记录使用 Agent 后的审阅、纠正、等待、接管和重新输入时间，不只统计生成时间。
对比使用等价任务与数据难度；同一个人重复做同题会学习，采用交叉顺序或等价题组。
预先说明希望改善哪项指标，以及最多接受多少错误、等待和额外复核成本。
没有实际用户基线时标记“效果尚未验证”，不要用 token 节约代替业务收益。

## 2. 建立可追溯 case 契约

每个 case 是版本化数据，至少包含下列字段；模型回答不能充当 expected 字段。

| 字段 | 内容 |
|---|---|
| `case_id / task_family` | 稳定 ID 和业务类别，避免只挑好做的题 |
| `principal / tenant / permissions` | 运行身份、资源边界和允许动作 |
| `initial_state / fixture_version` | 可恢复的真实语义数据；含资源 revision |
| `request / followups` | 用户任务、必要澄清和页面动作序列 |
| `expected_effects / forbidden_effects` | 应发生和绝不能发生的业务变化 |
| `oracle` | 独立查询或断言，指向权威记录与检查时机 |
| `risk_tier / budget / deadline` | 风险、资源和时间约束 |
| `fault_schedule` | 注入位置、barrier、恢复步骤；正常场景可为空 |
| `human_baseline` | 可比人工记录，或未测量的明确标记 |

脱敏生产样本优先；合成 fixture 用于覆盖边界，必须保留真实业务约束和状态关系。
冻结一套保留集用于最终比较；开发调参失败样本不得偷偷移出统计分母。
模型、prompt、工具 schema、registry、策略、数据与适配器版本写入 run manifest。
不得用生产写权限跑破坏性测试；使用隔离租户、沙盒账户和可恢复测试业务数据。

## 3. 四层验证，各有独立用途

| 层 | 方法 | 能证明什么 |
|---|---|---|
| L1 确定性契约 | 假模型、真实 executor/状态机、边界值 | 权限、幂等、版本、终态和取消逻辑 |
| L2 集成与故障 | 真实适配器+沙盒后端，控制并发与断点 | 真实存储事务、丢响应、恢复和对账 |
| L3 模型任务 | 真实模型做业务任务，多次独立重复 | 意图理解、工具选择、澄清、质量与稳定性 |
| L4 人机工作流 | 代表性人员完成相当任务 | 净人工收益、信任、接管、操作错误 |

L1 通过不证明 L3；脚本化模型能稳定输出正确工具，也不能证明真实模型行为。
L3 的好答案不证明 L2 的业务提交；浏览器展示 receipt 不证明后端确实写入。
L4 不能只请开发者沿预定脚本演示；包括实际会使用该系统的人员和意外路径。
无法运行某层时记录缺口与阻塞，不以其他层的数量冒充覆盖。

## 4. oracle 独立于模型和 UI〔H04、H06〕

写操作的 oracle 读取业务主表/API、operation ledger、批准记录与版本变化。
对照 expected effects 逐字段校验，并查 forbidden effects、资源总量和跨租户记录。
重复提交场景同时数业务副作用和 ledger 记录；只验证返回同一字符串不够。
通知、付款或外部提交必须有沙盒供应商侧的独立查询记录；本地“已发送”日志不够。
unknown 场景以最终权威状态收敛为成功，不要求立即成功，也不允许直接判失败后重做。
UI oracle 检查 partial 无写动作、操作结果与 receipt 一致、stale 显示及事件缺口处理。
保留截图或 DOM 断言帮助解释 UI，但不要用截图代替业务状态核验。
对推荐/解释类任务，可用来源一致性、约束满足、事实错误率和人工盲评 rubric。
模型裁判只能辅助软质量评分；权限越界、重复写、审批失效必须由确定性 oracle 判定。

## 5. 重复与统计，不把一次成功当稳定〔H10、H11〕

开发快速反馈可先每题 3 次；版本候选至少每题 5 次，关键高变异路径追加样本。
以上是起始采样量，不是可靠性保证；按目标错误率和置信区间决定实际样本规模。
每次重建独立状态、清空不属于场景的 memory，并随机化题目顺序，避免缓存泄漏答案。
专门评测跨回合 memory 的 case 应保留约定历史，并把历史作为 fixture 的一部分。
固定模型配置以便归因，同时单独做允许配置范围内的鲁棒性试验。
报告每题成功率、完全成功率、严重失败数和区间；不能只给全题平均值。
零次观测失败不代表失败概率为零；例如 0/n 的粗略 95% 上界约为 3/n，且依赖独立性假设。
按业务类别、风险、语言、数据规模、延迟条件分层汇总，暴露被平均数掩盖的弱项。
每次失败保留输入、输出、事件轨迹、工具参数、业务前后快照和可复跑种子/注入顺序。
回归使用同题配对比较，报告改进和退化；不得只补通过用例却忽略旧路径下降。

## 6. 人机风险分层与门槛

| 层 | 示例 | 放行依据 |
|---|---|---|
| R0 只读 | 查记录、解释政策 | 权限、事实准确性、来源和响应 SLO |
| R1 可逆低影响 | 保存草稿、修改个人视图 | 已有授权、幂等、可验证撤销、用户收益 |
| R2 业务变更 | 排班、资源分配、批量字段更新 | 明确范围、版本控制、影响预览、策略所需批准 |
| R3 高后果 | 资金、外部发布、不可逆操作 | 业务定义的强授权与批准、严格限额、对账、接管演练 |

具体分层由业务负责人和已有制度决定；不能凭领域名称把所有动作统一升到最高风险。
人工批准只解决授权判断，不抵消后端重复写、过期版本、未知结果和越权缺陷。
关键硬门：未授权影响、跨租户读取、重复不可逆写、错误已提交回执必须为零观测失败。
发现此类失败应停止对应能力的放行，先修复再重新运行受影响层与回归集。
软质量门槛、可接受失败率、p95 延迟、unknown 最大时长和人工接管比例由项目提前填写。
不能在看到结果之后放宽门槛并仍称同一版本通过。

## 7. 业务 SLO 与效率指标〔H09、H11、H12〕

至少报告：约束内任务完成率、正确提交率、错误作用率、unknown 收敛率与收敛耗时。
同时报告首次可用结果时间、最终确认时间、p50/p95、单任务成本、预算超限率和取消耗时。
按失败原因拆分人工接管、重新确认、重新输入、人工改正和系统重试，不能合成“用户互动”。
净人工节省 = 人工基线主动时间 − 使用 Agent 后操作/审阅/纠错/接管的主动时间。
端到端加速与人工节省分开报告；模型快但要求大量复核，可能没有净收益。
衡量错误的业务代价与返工，不把“工具成功调用率”当作最终效益。
上线后监控同一组指标；出现数据漂移、供应商变更、模型升级需重跑相关任务层。

## 8. H01–H12 对证据的最低要求

H01 身份租户：越权请求被拒，其他租户无泄漏；H02 幂等：重复意图仅一次副作用。
H03 版本审批：过期版本/批准被拒；H04 原子对账：部分提交、丢响应后结果可收敛。
H05 会话撤销：旧流不能复活会话；H06 UI receipt：显示成功与权威业务提交一致。
H07 新鲜度：动态事实变化会使旧动作失效；H08 记忆：删除/更正不会被旧任务撤销。
H09 预算：并行和重试也守限；H10 坏模型意图：恶意/错误工具参数不能突破业务约束。
H11 效率：有可比人工基线和净收益；H12 观测降级：可定位、可恢复、失败时不冒进写入。
每项关联至少一个 case ID、一次结果和 artifact；“已考虑”不是证据。

## 9. 交付与复跑

输出 manifest、case 集、oracle 实现、各层结果、故障矩阵和代表性失败轨迹。
报告分为已验证、未验证、已知失败；每个失败写修复位置、责任边界和重新验收条件。
回归跑过后才将修复标为闭环；标注探针断言的是“缺陷存在”还是“修复后正确行为”。
上线建议注明允许的业务/风险范围，不把某一沙盒场景的通过扩展为整个平台可生产使用。
