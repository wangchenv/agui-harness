# 视觉系统、组件和可访问性

本文件用于从线框走向可运行界面；按现有技术栈落地，不规定某个 CSS 框架或组件库。
安全状态和核心可访问性使用 **MUST**；其余是可判断、可调整的设计准则。

## 1. 先继承，再决定变化

检查项目现有设计 tokens、样式变量、组件、图标、字体和典型页面，记录可复用路径。
有设计系统时保持品牌、语义颜色、组件交互及排版节奏；确有问题再提出局部变更和影响范围。
没有设计系统时，基于任务频率、信息密度、信任需求和设备形成明确视觉方向。
“清晰紧凑的操作台”“强调阅读与来源的调查界面”都是方向；具体方案应落到信息层级和组件。
避免默认渐变、大量阴影、装饰图、统一圆角卡片堆叠；这些只有在帮助识别与阅读时才使用。
用户未指定偏好时，制作可查看的方案并说明选择，不凭空声称已获得品牌认可。
资产优先复用项目内容；不自动使用付费设计、图片生成或素材服务。

## 2. 让视觉层级跟随任务

主操作、对象标题、关键事实与执行状态应有清楚优先级，不让装饰抢过业务信息。
排版区分标题、正文、辅助说明、表格数值和状态；尺寸与行高服务阅读，不机械增加层级。
中文正文检查标点、换行与英文/数字混排；金额、时间和 ID 的格式由领域规则决定。
密集表格可使用等宽数字，长 ID 提供可访问的完整值和复制反馈；不要用无限缩小字体塞内容。
用稳定间距表达分组，用对齐表达关系；关键差异和前后值放在容易比较的位置。
语义颜色保持一致：成功、警告、错误、信息、待核实和中性状态不会随页面换含义。
**MUST** 状态同时有文字或图标/语义标签，不能只以红绿或位置表达。
层级、密度和留白可适应审查/探索/办理任务；不强迫所有页面采用同样的卡片网格。

## 3. tokens.json

输出可被实现采用的 tokens，或生成现有设计系统的映射；不要维护一份与代码脱节的颜色清单。
以 [tokens 模板](../../../templates/tokens.json) 为结构起点，并满足 [ui-tokens.schema.json](../../../schemas/ui-tokens.schema.json)。模板颜色和字体只是示例，不应覆盖项目风格。
必需分组为 `schema_version`、`color`、`typography`、`spacing_px`、`radii_px`、`breakpoints_px`、`contrast_pairs`、`motion`；精确字段与限制以 schema 为准。
`color` 中的 canvas/surface/text/primary/focus/danger/success 等是语义角色；在 `DESIGN.md` 记录它们映射到现有设计系统的哪个变量及消费位置。
审计文件使用已解析的 `#RRGGBB` 颜色，不能把 CSS `var(...)` 直接写入该字段；来源、别名关系、主题和额外语义说明保留在现有系统及 `DESIGN.md`。
记录单位：尺寸字段按名称使用 px，`line_height` 是无单位倍率，动效时长是 ms。实现可采用 rem 等适配单位，但应说明与审计声明的映射。
不要向关闭扩展字段的 schema 添加任意键；阴影、层级、内容宽度和密度等未收录设计仍可在项目样式系统及设计文档中定义。
多主题应用同时验证各主题；已有深色模式不得因新增组件失去可读性。
token 的具体数值是设计选择；通过实际渲染、对比度和内容压力检查证明适用。

## 4. component-inventory.json

清单连接设计、实现和验证，复用组件不要求重新实现。
从 [组件清单模板](../../../templates/component-inventory.json) 开始，满足 [ui-inventory.schema.json](../../../schemas/ui-inventory.schema.json)；顶层为 `schema_version`、`components`、`screens`。

| 字段 | 内容 |
|---|---|
| `components[].id / purpose` | 稳定组件名称、支持的用户任务 |
| `components[].states` | 适用状态名称；进入/退出依据和文案以组件 ID 关联到 DESIGN.md |
| `components[].actions` | `id`、`effect`、`allowed_states`、`result_source`；业务写的结果来自 receipt |
| `components[].accessibility` | `keyboard`、`accessible_name`、`focus` 的实际约定 |
| `screens[].id / role / primary_task` | 页面、使用者和主任务 |
| `screens[].components` | 引用已定义的组件 ID |
| `screens[].responsive` | mobile/tablet/desktop 的内容排序、折叠、滚动和操作安排 |

复用来源、变体、实现路径、数据权威源、期限、验证位置等在 `DESIGN.md` 按组件 ID 补充，不能作为任意附加字段塞入清单。

这里的清单字段不是 AG-UI 协议，也不能替代后端 registry、权限和组件 schema。
运行 [ui_audit.py](../../../scripts/ui_audit.py) `--tokens PATH --inventory PATH` 检查声明：结构、颜色对、引用、partial/unknown 等状态禁写以及写成功依赖 receipt；仍需浏览器验证实际 DOM 和状态处理。
涉及生成组件时，事实补全、partial 限制和 receipt 遵循 [交互契约](../../agui-build/references/interaction.md)。

## 5. 完整交互状态〔H06〕

按组件实际行为设计状态，不只绘制默认态和成功态：

- 输入/选择：默认、hover、focus、选中、禁用及原因、校验错误、待保存；长内容和空值可理解。
- 数据展示：初始、加载、空结果、部分数据、有效结果、刷新、stale、无权限、读取失败。
- 执行动作：建议、待业务所需批准、提交中、committed、明确失败、unknown、取消待核实、已确认取消。
- 结果与恢复：批次部分成功、可重试读取、冲突后重新检查、无法撤销与补偿结果。

**MUST** 不以乐观成功提示冒充业务提交；可以乐观更新本地草稿，但要能区分未保存状态。
**MUST** unknown 显示核实进度与查询/接管入口；重复点击不能创建第二次业务副作用。
**MUST** partial、过期和被拒绝的动作在交互处理层失效；仅把按钮绘成灰色不够。
加载时保留已知上下文，错误说明保留可恢复输入；不要让整屏 skeleton 每次刷新重置用户位置。
文案描述可观察事实与下一步；错误编号可以辅助支持，内部栈、权限令牌不得暴露。
反馈速度、等待说明和取消入口与实际执行能力一致〔H09〕，不显示虚构百分比。

## 6. 响应式与内容压力

断点由内容何时拥挤决定；使用项目断点可减少不一致，但仍需验证真实宽度。
检查桌面、移动和至少一个中间宽度；长标题、长译文、大数值、多行错误都应可读。
桌面侧栏可在移动端变为顺序步骤或可展开区域，关键对象和状态保持可定位。
表格需要比较关系时允许局部横向滚动并提供提示；不要把每行机械改卡片而丢失比较信息。
**MUST** 核心操作不能只能 hover 触发；触屏、键盘都能发现并使用。
**MUST** 页面缩放、软键盘、固定页脚和弹层不能遮住当前焦点及提交/取消控件。
触控目标使用项目明确的最小尺寸和间距，检查密集操作的误触风险；不要仅按视觉图标尺寸判断。

## 7. 可访问性是交互行为

**MUST** 优先使用正确的原生按钮、链接、输入、标签、标题层级和表格语义。
**MUST** 键盘可走完核心任务，无非预期焦点陷阱；弹层打开后合理移入焦点，关闭后返回触发点。
**MUST** 焦点可见且不被遮挡；错误与必填要求关联到对应输入，错误摘要能定位问题字段。
**MUST** 图标按钮有可辨名称，忙碌/提交结果以适当状态语义通知；流式每个 token 不逐字打断读屏。
**MUST** 状态更新不擅自抢焦点；重要错误可以按任务需要引导焦点并保留上下文。
**MUST** 正文与背景、控件边界、焦点和状态标识满足项目可访问性对比度要求；没有要求时至少采用正文 4.5:1、大字及关键非文本标识 3:1 的项目基线，并记录测量方式。
**MUST** 尊重减少动态效果偏好，不能依赖动画传递唯一状态或强制用户等待装饰性动画。
上述检查不能单独证明符合某个完整可访问性标准；读屏和实际操作仍需 [验证](usability-validation.md)。
