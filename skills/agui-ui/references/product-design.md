# 从用户任务决定界面

本文件用于新界面、旅程重构和复杂任务的产品设计；简单组件调整只取相关部分。
设计准则用于作出可解释的选择，不要求所有项目出现相同页面或相同数量的研究文档。

## 1. 使用者与工作环境

先区分最终用户、运营人员、审查者和异常接管者；同一人可承担多个角色。
记录角色的目标、业务权限、使用频率、熟练程度、设备、注意力和工作中断条件。
人物画像以任务约束为主，不凭空编年龄、性格或动机；把访谈事实与设计假设分开。
读取已有任务记录、支持工单、界面和操作规程；没有用户研究就注明假设并用原型验证。
运营需求常包括批量处理、查原因、筛选异常、保留上下文和交接；不要只设计首次使用的成功演示。
同一界面服务多个角色时，说明共享信息与角色专属动作；前端隐藏按钮不能替代后端授权。

用轻量任务表保留决策依据：

| 项目 | 应回答的问题 |
|---|---|
| 角色与环境 | 谁做，桌面还是移动，独立操作还是中断频繁？ |
| 触发与目标 | 为什么现在做，什么业务事实表示完成？ |
| 当前基线 | 现有入口、步骤、等待、审阅与常见返工是什么？ |
| 必要信息 | 哪些事实必须可见，来自哪里，多久失效？ |
| 控制与授权 | 可以直接做什么，哪些条件下才需批准？ |
| 例外与接管 | 数据不足、权限不足或结果未知时怎样继续？ |

真实权限和业务成功定义采用 [架构与责任边界](../../agui-design/references/architecture.md) 及项目契约。

## 2. 信息架构先于页面装饰

将用户语言映射到稳定业务对象、对象关系和常用入口，不直接把工具/API 名称当导航。
区分长期导航、任务内步骤和当前对象上下文；不要让用户通过聊天历史寻找所有历史操作。
明确哪些视图是权威对象详情，哪些是临时比较、建议或操作预览。
搜索、过滤、排序、最近访问和收藏只在有明确任务价值时加入；小任务不需要完整后台导航。
让使用者知道“我在哪、正在处理谁、已改变什么、接下来能做什么”。
多人或多租户环境 **MUST** 清楚呈现当前业务范围，切换后不保留可误用的旧操作上下文。
页面层级应适应角色，而不是将用户、运营和审查三种任务硬塞同一屏。

## 3. 按任务阶段选择布局

以下是选择依据，不是固定模板：

| 任务形态 | 适合的界面组织 | 主要判断 |
|---|---|---|
| 发现与探索 | 搜索/筛选、结果列表、比较视图、上下文解释 | 能否缩小范围、看来源、比较约束？ |
| 执行与办理 | 对象详情、结构化表单、计划/步骤、影响预览 | 能否准确修改、检查输入并知道生效边界？ |
| 审查与复核 | 前后差异、证据、例外队列、可展开批次结果 | 能否定位变化、理解风险、逐项处置？ |

工单排障可用“对象详情 + 调查时间线”；资源预约可用日历/时间段；CRM 跟进可用记录与待办。
只有用户确实监控汇总趋势和异常时才做仪表盘；不要先放统计卡片再寻找用途。
复杂任务可以在阶段间切换布局，但保留所选对象、过滤条件、未提交输入和来源上下文。
移动端常需要先处理一个对象再展开细节；不要仅缩小桌面多栏页面。

## 4. 自然语言与传统 UI 共存

自然语言适合描述目标、提出约束、调查原因和解释取舍；它不应成为已知字段的唯一输入方式。
筛选、日期、数量、批量选择、排序、字段校验和前后差异通常提供直接控件更容易检查。
让对话形成可编辑的结构化提案；用户修改表单后，对话看到同一对象的新版本。
聊天与页面动作 **MUST** 经过同一业务执行路径和状态源，不允许各自“成功”却更新不同记录。
解释区域可以折叠；影响决策的目标、金额、期限、关键差异和执行状态应在主阅读路径可见。
提供恰当的手动操作与接管入口，不要求用户反复重写提示词才能纠错。
提示建议可以帮助入门，但不要让“推荐下一步”悄悄扩大已授权范围。
对话入口的位置由任务决定：探索可能占主区，高频结构化办理可以放次级区域。

## 5. 旅程与恢复路径

先画一条可完成任务的低保真线框，再补最重要的例外；说明信息顺序和交互，不急于装饰。
旅程至少涵盖进入、识别对象、补齐信息、形成决定、执行/等待、核验与继续工作。
读操作可以在信息获取后结束；不要为流程完整而虚构审批或写入步骤。
**MUST** 将建议、批准、提交、权威确认分开；具体状态以 [交互契约](../../agui-build/references/interaction.md) 为准。
跨页或刷新恢复时保留可恢复的业务状态；未知结果先查询，不重新发送同一业务请求。
批准过期或对象变化时展示具体差异和新的选择；不默默套用旧批准。
部分批次成功时逐项列结果，给失败和未知项合适出口；总标题不能掩盖未完成项。
用户离开页面或点取消时显示已知事实，不声称外部操作已回滚。

为每个关键转折记录：用户问题、当前证据、可行动作、反馈、下一状态和错误出口。
按用户注意力控制确认成本：已有授权的低影响操作可直接执行，明确高后果变化再按业务策略确认。
设计撤销时先查实际可逆性；只能补偿的动作应说明补偿后仍存在的影响。
运营接管要携带对象、operation、已尝试步骤和未决状态；不要求再次询问全部上下文。

## 6. 把设计变成可查看的方案

视觉偏好缺失时提出一个适合任务的主方案和取舍，例如“保留现有品牌，用紧凑列表提升批量审查”。
只有实质不同的任务安排才值得比较方案；不用三套换色稿代替思考。
先制作关键页面与关键状态的线框；可用 HTML、项目组件或已有设计工具，不强制某种格式。
线框通过自查后继续实现可运行原型；用户反馈到来时调整，不能把等待形式审批当成默认停止点。
原型使用有代表性的隔离数据：长标题、多语言、零结果、权限不足、等待和未知结果。
原型中的模拟写操作 **MUST** 可辨识为模拟；演示“成功”不得被报告为真实业务完成。
复用已有应用入口时注明原型路由和启动命令；不要引入第二套不可维护的演示架构。

## 7. DESIGN.md 的推荐内容

可从 [ui-design.md](../../../templates/ui-design.md) 起步，组织结构也可适应已有文档；以下问题应能找到答案，不要求复制标题：

- 范围与证据：目标任务、用户材料、假设、现有设计系统与约束。
- 角色与信息架构：核心对象、页面/路由、角色差异和主要入口。
- 旅程与线框：关键步骤、成功依据、失败/恢复、移动差异。
- 设计取舍：布局为何适合任务、自然语言与控件如何分工、视觉方向。
- 组件与状态：链接 inventory，说明哪些由事实驱动、哪些允许模型组织。
- 实施与验证：tokens/原型路径、启动方式、截图、检查记录及未验证项。

产品质量判断：重要内容能否找到、变化能否理解、决定能否检查、异常能否继续。
不要把文档页数或组件数量当完成标准；用 [可用性验证](usability-validation.md) 检验实际任务。
