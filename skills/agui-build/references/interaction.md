# 交互契约：模型组织界面，业务系统确认事实

本文件用于实现面向业务人员的 Agent 界面；控制编号沿用 H01–H12。
先在目标项目记录组件、状态和动作契约，再改前后端；不要用演示卡片代替真实业务闭环。
运行时约束见 [runtime.md](runtime.md)，可执行故障验收见 [failure-matrix.md](../../agui-verify/references/failure-matrix.md)。

## 1. 先定义一个可完成的业务动作

为每个动作写出：操作者、资源、允许的变更、前置条件、成功事实、失败事实和撤销边界。
例如“提交维修工单”的成功事实是工单服务返回可查询的工单记录，不是模型说“已提交”。
同一界面可以同时显示调查结果、待批准建议和已执行回执，必须明确标识各自含义。
沿用用户在当前任务中已给出的授权；低风险且已授权的动作可以按策略直接执行。
只有权限、策略或具体高风险后果要求时才设置人工批准，不要为所有写入增加确认弹窗。

## 2. 组件 registry 是唯一渲染入口〔H06、H10〕

每个组件登记以下内容，提交时同时评审服务端定义和前端实现。

| 字段 | 必须说明的内容 |
|---|---|
| `component_id` / `schema_version` | 稳定名称和版本；未知版本的明确降级方式 |
| `model_input_schema` | 模型允许选择的 ID、排序、说明；长度、枚举和数量上限 |
| `view_schema` | 服务端补全后的完整载荷；与前端类型一致 |
| `enrich` | 从哪些授权数据源取事实；缺失、过期、拒绝时怎么处理 |
| `actions` | 可展示的动作类型；服务端前置条件与绑定的业务对象 |
| `partial_policy` | 能渐进展示的字段；禁止出现的写动作 |
| `freshness_policy` | 快照版本、有效期、刷新触发条件 |
| `fallback` | 无法渲染时显示的安全文本或状态查询入口 |

模型只引用已由服务器解析并授权的实体 ID，不接受模型提供的价格、权限、库存作为事实。
`enrich` 再次按当前 principal 和 tenant 读取或验证对象；“模型见过”不等于仍有访问权〔H01〕。
数值、期限、额度、状态、计算合计来自后端；模型可写解释，但解释不能覆盖机器字段。
禁止让生成内容携带可执行脚本、任意 HTML、任意表单目的地址或权限 capability。
外链由服务端按目标域和上下文校验；前端不把模型生成 URL 当作结算或批准入口。
未知组件应显示“不支持此内容”并保留关联 ID，不能悄悄当作已完成动作。
部分结果和最终结果使用同一事实来源；最终结果需要完整 schema 校验和业务校验。
呈现工具原则上不写业务状态；若必须保存计划，另设明确的 proposal 操作并可审计。

## 3. 分开维护三类状态〔H06〕

三类状态分别存储；UI 不能从一类状态推断另一类已经成功。

| 状态对象 | 建议状态 | 唯一可信的推进依据 |
|---|---|---|
| turn | `running / completed / failed / cancelled` | 编排器的有序事件与服务端运行记录 |
| operation | `proposed / approved / executing / committed / rejected / failed / unknown / cancelled` | 业务执行器与权威业务记录 |
| presentation | `partial / validated / final / interrupted / stale` | 组件校验结果、事件完整性和数据新鲜度 |

`turn.completed` 只表示本轮计算结束；可能产生建议、失败解释，或者结果未知的操作。
`presentation.final` 只表示组件载荷完整且被校验；proposal 的 final 卡仍然是待执行建议。
`operation.committed` 必须由后端 receipt 支撑，不接受模型文本、工具开始事件或动画完成。
`failed` 表示已经确认该操作没有生效；外部请求发出后响应丢失，应进入 `unknown`〔H04〕。
`cancelled` 需要证明没有生效或已完成约定的取消；用户点取消不自动意味着已回滚。
`unknown` 显示“正在核实结果”，提供查状态和人工接管；不能显示“安全重试”。
失败或中断时清除待定 skeleton，但不要将残留 partial 自动提升为 final。

## 4. partial 只能帮助阅读〔H06、H10〕

partial 可以逐步展示说明、只读候选项、已授权的数据行和加载进度。
partial 不显示或启用任何会改变业务状态的按钮，包括批准、提交、领取、保留资源和发送。
前端必须在状态分支中阻断动作，不仅把按钮变灰；服务器始终独立检查动作能力。
final 卡启用动作前需拿到服务端生成的有效 proposal/action handle，而不是模型自报的 ID。
模型修改同一 partial 的标题、行数或推荐时，不能悄悄改变已经批准的 proposal。
完整校验拒绝后将该卡标 interrupted/rejected 并解释原因；不要保留看起来有效的动作。
最后一帧是 partial、连接 EOF、解析错误、超时均不能冒充完整结果。
已收到有效 final 的卡可以保留；整轮缺失终止事件时仍显示“本轮未完整结束”。

## 5. proposal、批准与 receipt〔H02、H03、H04〕

proposal 由服务器建立，包含目标对象、预期版本、变更前后值、影响范围、失效时间和内容摘要。
批准绑定 `proposal_id + proposal_revision/hash + actor + tenant + expiry`，不是绑定自然语言“同意”。
批准后修改目标、数量、金额或范围必须产生新 revision；旧批准不得复用。
风险分级决定是否需要批准；无需人工批准时也记录策略授权依据，不伪造人工批准者。
UI 提交意图时生成或取得稳定 `operation_id`；双击、重发和恢复使用同一个 ID。
服务端将 operation ID 与 principal、payload hash 绑定；同 ID 不同载荷应明确冲突。
receipt 是服务器读取执行记录后产生的投影，至少关联 operation ID、确认状态和结果版本。
可包含业务引用号、已生效字段和提交时间；不要把权限令牌或内部错误栈发给前端。
receipt 未到时显示“提交中/核实中”；仅当权威记录确认提交才显示“已生效”。
若动作部分完成，逐项展示已完成、失败和待核实；不能用一个成功图标覆盖整个批次。

## 6. 流和刷新恢复〔H05、H06、H12〕

应用定义稳定 `stream_id`、单流递增 `seq`、去重用 `event_id`，并关联 session epoch 和 turn ID。
事件先进入可恢复日志，再对客户端确认相应可恢复状态；保留策略必须覆盖声明的恢复窗口。
客户端保存最后连续应用的 seq；重复事件忽略，发现间隙暂停依赖它的动作并申请重放。
不同流的 seq 不比较大小；业务对象的新旧由业务 revision 决定，不由到达顺序决定。
恢复接口鉴权后返回快照及一致的事件游标，避免快照和重放之间漏事件或重复执行。
日志过期时返回显式 resync，客户端用快照重建，不自动重新发送原来的写请求。
刷新后恢复 operation 状态与 receipt；不能靠重新运行用户消息来恢复界面。
断线与页面卸载应停止本地订阅；是否取消服务端工作由运行策略决定，不能默认已撤销。
注销、重置或切换身份后，旧 epoch 的响应、事件、缓存和动作 handle 全部失效〔H01、H05〕。

## 7. 新鲜度与页面操作〔H07〕

每张依赖动态事实的卡标明资源 ID、版本和查询时间；预约/报价还需有效期。
提交前服务端重新校验版本、余额、资格、库存或占用关系；TTL 内也不能跳过必要约束。
数据变化时先把旧卡标 stale，刷新后展示变化；涉及已批准字段变化则要求新批准。
旧预约卡必须绑定其 reservation ID，不能借用“当前所有预约”的倒计时显示仍有效。
页面动作和聊天动作经过同一业务执行器，业务规则、幂等和权限不能有两套。
页面动作写入有 ID 的 app event；聊天只记录消费游标，不能覆盖尚未消费的事件。
遇到聊天中的并发页面变更，可以提示事实已更新；不要为一致性假装该动作没有发生。

## 8. AG-UI 适配边界

[AG-UI 事件](https://docs.ag-ui.com/concepts/events)可承载运行生命周期、文本、工具和状态同步。
采用它时增加 adapter，业务状态机和 registry 保持独立；也可以使用已有 SSE/WebSocket 协议。
`RUN_FINISHED` 仅作为 run/turn 结束信号，不能映射为 `operation.committed`。
proposal、receipt、seq 恢复约定和业务 revision 是本项目扩展，不宣称为 AG-UI 官方标准字段。
在项目协议文件记录扩展载荷、版本、能力协商和旧客户端降级；未知扩展不得触发写入。
协议适配测试验证事件映射、重复和缺帧；业务验收仍查询权威业务状态，而非检查事件名称。

## 9. 完成证据

交付 registry 条目、状态转换表、一次成功 receipt 和一次中断恢复轨迹。
同时演示 partial 无写动作、失效批准被拒、刷新不重复提交、旧身份事件被丢弃。
把新组件场景加入故障矩阵；只有视觉截图而没有业务状态断言不能作为完成依据。
