# 会议设备预约：UI / UX 设计契约

状态：设计完成，尚未生成或打开原型，未取得浏览器、截图、读屏或真实人员效率证据。
范围：员工查设备并提交自己的预约；园区管理员建议替代/驳回冲突请求；不支持强制抢占已确认预约。

## 1. 角色与成功任务

设计假设（尚无访谈）：员工每周低频使用，通常先知道会议时间与地点，再决定借哪台设备；优先减少找设备和核实结果的成本。
设计假设（尚无访谈）：管理员在冲突发生时处理队列，需要看清请求差异、管辖范围及已处理状态；信息密度可高，但不隐藏关键时间。
员工成功：在准确时间与地点获得明确预约号，或基于真实证据知道未预约、需要澄清/改条件。
管理员成功：将待处理请求明确记录为建议替代/驳回；员工不会把建议误认为设备已被占用。
现有人工基线尚未测量；后续以真实目录/日历/工作台同任务计时，包含核实与纠错时间，禁止使用估算数字宣称收益。

## 2. 信息架构与主操作

导航为“查找设备”“我的预约”；仅有管理员权限者出现“冲突处理”。组织/园区身份固定在页头可核对，不把切换角色做成演示按钮。
助手是可折叠的辅助区域，负责输入自然语言需求、解释选择与澄清，不替代结构化筛选和预约结果入口。

| 屏幕 | 主要判断 | 主操作 | 关键证据 | 返回确定性流程 |
|---|---|---|---|---|
| employee-search | 哪台实物在指定地点/时间满足需求 | 查询设备；选择某台 | 实物名称/编号、地点、设备能力、证据时间、完整区间 | 时间/园区/类别表单始终可用 |
| employee-review | 将给自己占用哪台设备、哪个区间 | 提交预约 | Host确认的设备/借用人、日期/时区、方案有效期 | 修改条件后生成新方案，旧批准失效 |
| employee-operations | 刚才是否真的预约成功 | 查看结果/核实进度 | operation状态、后端预约号及准确区间 | 无需重新提问助手即可刷新查询 |
| admin-conflicts | 处理哪条请求、建议是否合适 | 记录建议或驳回 | case版本、原请求与建议的对比、候选证据 | 普通列表/筛选/决定表单 |

初始屏幕不预填虚构预约与员工数据；原型未来若用 fixture，须标注“演示数据”，不得显示成已连接企业系统。

## 3. 关键界面布局

桌面员工页：顶部身份与导航；左侧主区域为标题、时间/园区筛选和设备列表；右侧 360px 审查区仅在选中设备后出现。
没有选中设备时让列表占满可用宽度，助手默认折叠在右下角帮助入口，避免空审查框挤压列表。
设备列表每项按“名称与编号 → 地点 → 主要能力 → 当前区间可用性 → 选择”排序；不以商品价格卡/购物车隐喻呈现。
确认区始终显示带日期的开始/结束与时区；借用人来自登录身份，不能在模型生成表单中编辑。
“提交预约”紧邻准确摘要与有效期；禁止一屏多个竞争主按钮，清空筛选/修改条件均为次级动作。
未知结果使用固定状态区显示“正在核实预约结果”，带 operation引用与上次核实时间；无“再预约一次”主按钮。
已确认结果显示预约号与设备/区间，使用可复制文本，不提供本期未实现的取消或改期按钮。

桌面管理员页：左侧 320px 冲突队列，右侧请求详情与原请求/建议差异；助手说明默认折叠。
队列显示请求编号、园区、原设备、完整时间、等待时长和状态；不展示无关会议用途或其他员工隐私。
详情顶部明确“处理请求不会移动已确认预约”；建议区用“原请求 / 建议方案”成对比较设备与时间。
“记录替代建议”为主动作，“驳回请求”使用文字明确的次级危险动作，要求理由；不是强制抢占入口。
管理员决定后显示 case receipt 对应“建议已记录 / 请求已驳回”，不使用“预约成功”文案。

## 4. 视觉方向与 tokens

视觉采用安静、清楚的企业事务界面：浅灰绿画布、白色内容面、深石墨文字、深青绿主操作，避免营销式大图与装饰渐变。
用户未提供品牌规范；这是可替换的临时设计方向，不冒充企业现有 design system。
所有颜色、字体尺度、间距、圆角、断点与动效从 ui/tokens.json 读取；不在组件中另写一套常量。
正文 16px/1.5，表格辅助文字 14px；关键时间和结果不缩小到12px；金额/价格并非本领域主信息。
层级为页面标题 28px、区域标题20px、条目名称16px、辅助信息14px；设备编号/预约号用可选文本呈现。
间距以 4/8px 为基础，字段组16px、区块24px、页面留白32px；control圆角8px、card圆角12px，不堆积阴影。
主色只用于当前主动作与选中状态；成功/失败同时显示图标和文字，不能仅凭绿/红辨认。
unknown不借用success色；使用普通深色文字、时钟图标和“正在核实”标签，视觉上与已确认严格分开。
文本/按钮/焦点颜色对均在tokens声明；这些静态不透明色检查不覆盖叠层、图片背景、hover和disabled的实际渲染。

### Token 消费映射（计划）

[ui/tokens.json](ui/tokens.json) 是当前唯一颜色/尺度定义；新项目没有旧design system可继承。
未来 `src/web/tokens.css` 构建映射 `color.primary→--color-primary`、`color.text→--color-text`，其余颜色同名映射；`src/web/layout.ts` 消费断点与间距。
尺寸字段是px、line_height是倍率、duration是ms；实现字体/间距可按16px根字号转换rem并保留缩放，断点按布局宽度使用px。
内容最大宽度、焦点线宽/偏移、交互目标高度目前在本DESIGN中定义；schema未收录的项不作为私自扩展键塞入tokens。

## 5. 组件与状态

ui/component-inventory.json 是屏幕/组件清单；equipment_results、booking_confirmation、conflict_review 对应已有运行时registry组件。
筛选表单、操作历史、冲突队列、助手面板、恢复提示是确定性页面组件，不需要为展示布局额外发明模型工具。

| 状态 | 员工看到什么 | 可执行动作 | 权威边界 |
|---|---|---|---|
| loading | 骨架与“正在查询设备” | 改条件或取消本次查询 | 不把空白当无设备 |
| empty | “此条件下没有可用设备”及查询时间 | 修改时间/地点后查询 | 有成功查询证据才可显示 |
| error | “暂时无法查询/提交”与明确原因 | 安全重试读取或回到表单 | 发送后写错误按unknown处理 |
| partial | 简短说明/骨架，标注生成中 | 无写按钮 | 不含可提交payload或成功徽标 |
| validated | 完整可信方案和有效期 | 唯一准确提交动作 | Host schema、身份、证据已验证 |
| submitting | “正在提交”，避免重复点击 | 查询进度或离开页面 | 禁按钮仅体验；服务端仍幂等 |
| committed | 匹配receipt的准确业务结果 | 查看/复制结果 | 不从模型文字推导成功 |
| unknown | “正在核实结果”，保留操作号 | 状态查询/返回操作历史 | 不能改成失败或新建重试 |
| stale / expired | “方案已过期，请重新核实” | 重新读取并生成方案 | 旧批准不可复用 |
| interrupted | “内容未完成，请刷新核实” | 恢复快照 | partial绝不升级final |

冲突review还包含editing状态，仅能修改决定草稿/查询候选；完成Host验证后才进入validated允许写。
主按钮必须在正确业务状态、有效授权与可见权限均满足时出现；隐藏按钮不替代服务端拒绝。

## 6. 精确交互与失败出口

员工选择设备 → 审查区显示完整日期/时区/地点 → 点击“提交预约” → 持久operation → receipt或明确失败/unknown。
修改时间/设备立即使旧方案和批准失效；重新查询后生成新方案，不能只更新卡片上的文字仍提交旧payload。
SLOT_CONFLICT明示“未预约，该时间段刚被占用”；给“查找其他设备”及自己的冲突请求入口。
审批不是每轮对话的弹窗：R2占用在准确确认卡上批准一次；查询和解释无需额外确认。
管理员先选请求 → 查询替代 → 对比原/建议 → 记录决定；员工之后仍需亲自确认新预约。
partial断线置interrupted并移除所有提交能力；已提交operation则保留unknown/processing并可独立恢复。
关闭页面/取消生成不表示取消预约；结果入口始终在“我的预约”中，文案明确“已发出的请求仍会核实”。
权限被撤销时禁用未发起动作并说明原因；已完成占用仍可在重新认证且有权限后查询。

## 7. 响应式布局与放大

断点tokens：mobile390、tablet768、desktop1280；同时验收320px最窄宽度与1440px宽桌面。
桌面≥1280px采用主内容+审查区；内容最大宽度1280px，间距随tokens，不让超宽行损害扫描。
平板768–1279px保留单主列；确认区在主内容下方，管理员队列可折叠，当前请求标题始终可见。
手机<768px采用单列“筛选/结果 → 审查 → 结果”步骤页，顶部有返回与当前步骤；不使用三列压缩版。
手机筛选用可折叠区但显示所选日期/园区摘要；提交按钮在摘要后原位出现，不用遮挡错误信息的悬浮底栏。
管理员手机页先队列后详情；返回保留筛选与滚动位置，对比从双列改为连续“原请求/建议方案”区块。
设备列表在小屏用有标签字段重排而非横向截断；时间/地点/错误全文可换行，ID过长可折行复制。
200%/400%缩放仍能完成任务，普通正文不出现整页横向滚动；未来日历若采用二维网格需单独设计等价列表，本期不引入。

## 8. 键盘与辅助技术

DOM顺序与视觉顺序一致：导航→查询条件→结果→审查摘要→提交→助手；不使用正tabindex改顺序。
所有字段有持久可见label和格式帮助；起止时间分别命名，时区独立显示，错误用aria-describedby关联。
日期/时间优先原生或已验证的可访问组件；手动输入可完成同一任务，不能只依赖拖拽时间轴。
按钮Tab聚焦、Enter/Space激活；设备选择用真实button/radio；列表不做只能鼠标点击的整块div。
选择设备后焦点移至审查标题（可程序聚焦），提交中不抢焦点；提交结束结果用polite live region一次性宣布。
错误优先聚焦错误摘要并链接具体字段；重新查询不得把键盘使用者无故送回页面顶部。
助手如以dialog展开则有名称、Escape关闭、焦点约束和返回触发器；桌面非模态辅助区不设置虚假focus trap。
断线/恢复状态提示使用status/live region；不逐token朗读，也不对重复seq重复宣布成功。
每个交互目标至少44px高，焦点轮廓3px并留2px偏移；focus颜色在surface/canvas及主按钮邻接场景实测。
遵循prefers-reduced-motion；关闭骨架闪烁/位移动画，状态变化由文字表达，不用持续旋转作为唯一信息。

计划原型路径prototype/index.html，尚未创建；设计门禁仅允许登记路径，不声称已有可运行界面。
未来原型用确定性fixtures演示loading/empty/error/partial/validated/submitting/committed/unknown/stale/interrupted全部状态。
检查tests/test_booking_ui.py计划使用真实浏览器，context.execution_mode=browser；不能用grep或JSON校验冒充浏览器结果。
responsive_layout：390×844、768×1024、1440×900及320px/400%放大逐任务检查遮挡/溢出/主动作可达，保留真实截图与失败定位。
keyboard_navigation：只用键盘完成员工查询→选择→提交以及管理员建议/驳回；断言focus顺序、可见名称与提交后恢复。
ui_state_recovery：partial断流无写/成功；提交后断流→刷新→snapshot恢复唯一receipt；重放重复/乱序seq不回退状态。
额外负向断言：unknown不能创建新预约；旧generation迟到卡片不能重新激活；管理员receipt不会显示预约成功。
浏览器中检查真实computed样式、焦点和元素可见性，视觉review检查层级/排版/遮挡，二者分别记录不能互相替代。
色彩检查、浏览器UI自动化、人工视觉review、真实员工/管理员任务效率分别产证据；一个通过不代替其他层。
